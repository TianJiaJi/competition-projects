## 二、工作区划分

```text
工作区/
├─ README.md
├─ apps/
│  ├─ mobile/        手机游客端
│  ├─ ops/           园方大屏
│  ├─ visitor/       游客触控屏
│  ├─ admin/         后台与演示控制
│  ├─ gate/          前线人员处置终端
│  └─ server/        单实例后端
├─ packages/
│  ├─ contracts/     接口、快照、消息的共享契约
│  ├─ client/        请求、WebSocket 和样例适配
│  ├─ ui/            视觉变量、基础组件
│  └─ scenic/        景区数据、二维地图、三维沙盘
├─ assets/           原始素材与来源记录
├─ docs/
│  └─ archive/       被替代的历史方案
├─ infra/            后续容器、集群及穿透配置
├─ scripts/          后续辅助命令
└─ experiments/      临时原型
```

树中应用和共享包目录目前只有说明文档。源码目录、依赖清单、锁文件及配置文件留到开发阶段再创建，不使用大量空文件提前模拟工程已完成。

`.local/` 在实际开发时创建，用于本机数据库、日志、发布包和临时产物；后续建立忽略规则，不提交数据库或实际环境配置。

### 2.1 应用与共享包边界

- 每个应用负责自身页面、路由、状态和业务交互；应用之间不直接引用源码。
- 应用通过共享包复用能力；共享包不反向引用应用。
- `contracts` 定义客户端与服务端共同理解的数据契约，不暴露数据库内部表结构，也不包含 Vue 或运行时服务逻辑。
- `client` 统一请求、错误处理、连接状态、重连后快照拉取和样例适配，页面不各自实现一套通信方式。
- `ui` 收纳视觉变量和稳定的基础组件；具体预约表单、核销状态流程留在各端。
- `scenic` 内部划分景区基础数据、二维地图和三维沙盘，并提供独立入口。手机读取点位与二维地图时，不带入 Three.js 和大屏资源。
- 功能先放所属应用；发现真实复用需求后再提取共享能力，不提前抽象通用业务框架。

### 2.2 文件与素材管理

- 方案、运行说明、交接说明进入 `docs/`；旧方案和 Word 原件保留，当前文档关系由索引说明。
- 图片、字体、模型保存到 `assets/`，同时登记来源、授权和使用端。
- 后续按应用声明复制所需资源到构建目录；原始素材、处理结果和部署产物分开，避免五端都携带完整模型包。
- 临时页面或效果验证放 `experiments/`，不加入正式 workspace 和镜像；选中后移动到对应应用或共享包。
- 密码、LLM 密钥、穿透令牌、SSH 凭据、真实环境配置均不进入仓库；后续只提交模板。

## 三、快速原型与后端边界

### 3.1 开发方式

日常只运行正在开发的一个前端和后端，保留五端一并启动的联调入口。页面早期可以显式选择样例模式，后续通过同一套数据契约接入服务端。

样例模式与真实服务模式明确区分。后端超时、断线或拒绝操作时，应显示实际状态，不自动回退成样例成功。跨端预约、核销、公告及场景操作只能以真实后端联调结果验收。

各端使用同源 `/api`、`/ws`。开发时由 Vite 转发；Compose 由入口代理转发；Kubernetes 由 Ingress 转发。页面不写死后端 IP 和部署域名。

### 3.2 单进程内的职责

| 模块 | 职责与边界 |
| --- | --- |
| 订单与核销 | 预约、状态转换、防重复提交与核销；关键操作立即持久化 |
| 数值仿真 | 接收统一业务时间与状态，计算规则变化；不依赖浏览器时钟，计算逻辑与 HTTP、存储分开 |
| 聊天 | 房间消息与广播，连接恢复后重新拉取近期消息 |
| 内容与管理 | 预置资料、公告、设施与管理操作，按简单身份边界返回数据 |
| LLM | 集中代理外部模型调用、流式响应、超时与错误；失败保留重试和预置知识入口 |
| 存储与运行状态 | SQLite 读写、快照恢复、运行空间隔离和统一版本号 |

实时模式与回放模式按独立运行标识、时钟、快照和现场订单隔离；不因为共用进程或数据库而互相覆盖。具体数值与补算规则继续遵循数据专项方案。

三维沙盘、聊天、LLM 不拆成独立服务。只有后续出现已验证的负载或维护需求时，再评估拆分。

### 4.3 容器和集群约定

- 五个前端各自构建镜像、Deployment 和 Service，复用构建模板。后端单独构建镜像。
- 新系统使用 `scenic-demo` 命名空间。前端默认在工作节点运行；副本调整和 Pod 重建演示只针对这些无状态前端。
- 后端固定单副本，采用 Recreate 更新策略，使用带 node2 节点亲和性的本地 PV 与 PVC；回收策略保留数据。容器内数据库目录统一为 `/data`。
- 本地卷不提供跨节点数据高可用；node2 不可用时，不能将空数据库的后端迁到其他节点并当作已恢复。
- Kubernetes 使用 Kustomize，后续分为基础配置、现有内网集群差异配置、kind 差异配置；首版不使用 Helm。
- Ingress 采用五个精确域名及 `/api`、`/ws` 路由。复用已有控制器，避免为新系统改变全局设置而影响旧服务。
- 新应用设置基础存活和就绪探针。依赖外部 LLM 的可用性不作为整个后端存活条件。

### 4.4 香港入口与穿透

香港使用独立 Compose 项目管理 Caddy、frps；node2 使用另一个独立 Compose 项目管理 frpc。frpc 主动连接香港，Caddy 接收 HTTPS 后将流量送入香港本机的穿透转发端口。

穿透转发端口仅绑定香港回环地址；公网开放 HTTP/HTTPS 及穿透所需的连接端口，不公开 Kubernetes API、Dashboard、SQLite 或其他管理入口。穿透连接使用认证和加密。

代理链必须保留原始 Host，并明确传递外部 HTTPS 信息；只信任约定代理来源，不盲目信任任意客户端提交的转发头。部署时重点验证 WebSocket、AI 流式响应、登录状态及重定向，避免代理缓冲或协议判断造成故障。

香港只承载入口，不保存业务数据库。公网访问依赖香港到内网链路，模型与图片加载性能需要实测；初期不新增 CDN、对象存储或独立资源服务。

## 五、开发、发布与数据隔离

| 场景 | 运行方式 | 数据边界 |
| --- | --- | --- |
| 日常开发 | 单端 Vite 与本机 Node.js 后端 | 本机开发数据 |
| 独立页面原型 | 单端与显式样例适配 | 样例状态，不冒充跨端后端结果 |
| 整套联调或现场备用 | Compose 五端、后端、入口代理 | 独立 Compose 数据卷 |
| 编排演练 | Docker Desktop 上的 kind | 独立 kind 数据卷 |
| 公网主展示 | 现有内网集群，经香港穿透访问 | node2 的正式演示卷 |

本机使用 ARM64，服务器使用 AMD64。后续本机构建两种架构对应的镜像，以同一发布版本标识前端、后端和配置；导出发布包，通过 SSH 传输后导入目标节点的 containerd。首版暂不建立镜像仓库，也不在控制面节点堆积构建缓存。

镜像需要在允许调度该应用的节点上可用。记录发布版本和前一版本，更新程序不删除数据卷；涉及数据库结构变化时先做一致性备份，并验证程序版本与数据兼容性。

部署、备份恢复、重置演示数据分别提供入口，普通启动与部署不自动重置业务。SQLite 采用支持一致性快照的备份方式，不直接复制仍在写入的单个数据库文件来冒充完整备份。

各环境独立运行，切换现场备用不会自动继承云端刚产生的订单。备用提前准备同版本程序、独立初始场景、局域网解析、可信 HTTPS 和入口二维码；现场断网备用不依赖公网穿透。
