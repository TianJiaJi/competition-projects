## 一、目标与交付

将 V1.1 中偏生产系统的要求替换为演示项目设计。本轮交付仍是一份 Markdown 文档。

项目定位：**可自由操作的高完成度网页原型，功能入口完整，关键业务跨端闭环，复杂结果采用预设内容和轻量规则。**

“PPT 级”指投入重心在视觉完成度、交互反馈和演示表达；最终系统仍为可以实际操作的网页，不是幻灯片文件。设计深度通过清楚的业务关系、统一的展示语言和完整的演示反馈体现。

明确采用：

- 主线精修，同时允许临场换选项、换顺序。
- 全端清爽现代风，保留低多边形三维沙盘。
- 跨端数据同步和多人聊天；人脸识别入园作为后续接入，本轮仅产品定义。
- 真实 LLM 知识问答，模板化游览路线。
- 真实轻量 Kubernetes，单实例后端。
- 后台关键操作实际联动，普通管理功能轻量实现。

## 二、保留的功能与简化方式

| 模块 | 用户能够完成的操作 | 简化后的实现 |
|---|---|---|
| 资讯与景点介绍 | 浏览、搜索、收藏、扫码查看 | 预置精品内容和图片，简单检索 |
| 入园预约 | 选择时段、预约、取消、改期、查看凭证 | 少量可配置时段及简单订单状态，保留余量校验 |
| 停车预约 | 预约停车场、核销进场、模拟离场 | 配额与实际空位分开维护，不模拟完整车辆行为 |
| 人脸识别入园 | 人脸识别确认入园身份 | 本轮不实现识别、采集及设备接入 |
| 前线人员处置终端 | 反馈开始处理、提交完成结果 | 人工安排工作，园方只读同步处理状态 |
| 手机二维地图 | 查询点位、查看设施、展示路线与位置 | 固定景区地图、预制路径和沿线位置动画 |
| 双大屏沙盘 | 旋转、缩放、选点、切换图层 | 共用低多边形模型与预设镜头，数据绑定统一场景 |
| AI 路线 | 设置偏好、一键生成、查看详情、重新推荐 | 从约 8 条精修路线中筛选，使用可替换的推荐说明模板 |
| 知识问答 | 自由提问、查看来源、追问 | 精选知识按景点及关键词选取，直接作为 LLM 上下文 |
| 聊天 | 全园及景点房间真实通信 | 单进程 WebSocket，预置模拟游客消息补充氛围 |
| 园方监控 | 查看统计、告警、空间定位及处理记录 | 共享热力沙盘与统一快照，前线完成后关闭本次事件 |
| 普通后台管理 | 搜索、筛选、详情、表单、保存 | 样例数据加简单增删改，不建立复杂审批和权限体系 |

### 2.1 功能边界

- 路线模板必须对应地图中的实际路径；关闭景点或道路后过滤相关模板，无匹配结果时明确提示。
- 知识库采用预置内容，不做向量数据库、上传解析和在线索引。
- LLM 失败时提供重试及预置知识阅读入口，不将预设回答显示成实时模型结果。
- 订单、公告、设施开关、调度、聊天撤回和禁言必须影响对应终端。
- 非关键管理页面保存后至少能够在本页重新查询，不用无效果的“保存成功”代替操作。
- 普通游客和工作人员保留简单身份及入口权限，不建立细粒度 RBAC。
- 入园继续采用免费分时预约；停车独立预约，不选择具体车位。人工讲解预约入口改为 AI 讲解。
- 厕所展示位置、空闲厕位、排队与预计等待，使用场景规则生成；不开发逐厕位传感器系统。
- 保留资讯、公共公告、客流、停车及厕所等展示，不恢复营收、售票和满意度业务。
- 手机端集成所有个人服务；游客大屏提供公共触控导览，不展示个人订单、内部预警或游客聊天记录。

### 2.2 真实功能、规则模拟与预设内容

| 类型 | 内容 | 设计要求 |
|---|---|---|
| 真实操作 | 登录、预约、取消、改期、核销、跨设备聊天、LLM 问答、关键后台操作 | 实际提交、保存并产生对应反馈 |
| 规则模拟 | 客流曲线、设施负载、预警、调度恢复、地图位置推进 | 从统一场景状态生成，保持跨端一致和基本数量关系 |
| 预设内容 | 景区资料、文物知识、路线模板、背景游客消息、镜头与剧情 | 提前精修，支持筛选、组合及可控触发 |
| 真实部署展示 | 子域名、容器、Kubernetes 前端副本及重建 | 展示实际状态，不增加业务后端多副本要求 |

入园方式改为人脸识别，采集、身份匹配和设备协议后续单独设计。前线人员处置终端不承担入园识别或扫码输入；园方大屏没有派单、确认或消除按钮。

## 三、极轻后端与可控场景

### 3.1 技术结构

采用 **一个 Node.js 服务＋SQLite＋WebSocket**：

- SQLite 保存演示账号、订单、聊天、后台修改及场景快照。
- 内存维护当前场景，关键操作后保存；启动恢复最近快照。
- 一个进程处理接口、背景数据更新和消息广播。
- 后端代理 LLM 请求，密钥不进入前端。
- 复用导师项目中的有用逻辑和素材，不要求兼容其所有旧接口或继续扩展旧架构。

前端采用 Vue 3、TypeScript、Vite，共享基础组件和类型；三维沙盘使用 Three.js，手机二维地图使用 SVG，图表使用 ECharts。景区模型、图片及其他静态资源随部署包发布。

删除 PostgreSQL、Redis、Outbox、独立 Worker、跨副本协调、分布式锁、完整游客行为仿真及生产级恢复要求。

### 3.2 场景驱动

设定“正常游览、展馆拥堵、停车紧张、厕所维修、降雨”五种场景。

每个场景包含背景曲线、设施状态、预警文案、公共公告、推荐路线和过渡时长。演示控制台提供：

- 开始、暂停、重置。
- 切换场景、触发事件。
- 跳转到主线中的指定步骤。
- 执行调度、恢复正常状态。

后台保存统一场景和变化起止时间，前端按时间平滑呈现，避免各屏独立随机。

保留最基本的数据逻辑：

- 入园核销增加在园人数，离园减少人数。
- 区域人数由统一总量及分配规则生成，合计一致。
- 停车预约不直接占用实际车位，核销进场才增加占用。
- 空位、厕位和排队人数不出现负数。
- 预警确认只改变处理状态；执行分流才启动恢复曲线。
- 手动业务操作形成独立增量，不被背景数据刷新覆盖。

不计算数千个游客个体、复杂排队模型或真实客流预测。前端可以展示场景预设趋势，但不将其描述为真实训练模型的预测结果。

常规切换场景保留现场操作产生的订单和人数增量；“跳转演示步骤”加载该步骤配套的完整样例状态，避免只跳页面却缺少订单或凭证。“重置演示”恢复统一初始状态，使全部终端能够重新走完主线。

### 3.3 最小接口

接口只围绕页面需要组织：登录、内容、订单、核销、路线模板、知识问答、聊天、后台管理、场景控制。

所有终端获取同一份带版本号的场景快照。WebSocket 负责通知更新和聊天；重连后重新拉取快照与近期消息，不实现复杂增量重放。

订单创建保留请求编号，核销保留订单状态判断，防止连点或扫码枪重复输入造成重复结果。请求超时后查询原结果或使用同一请求编号重试；无法访问后端时不显示核销成功。

普通工作人员入口校验登录身份，公开接口不返回联系人、个人订单或内部运营信息。该边界用简单角色判断实现。

## 四、前端精修与部署展示

### 4.1 视觉及交互标准

全端采用清爽现代风：浅色背景、明确的文字层级、克制的品牌色、高质量景区图片和统一图标。运营屏也不采用传统深色霓虹驾驶舱。

- 手机：贴近成熟文旅产品，重点打磨首页、地图、订单凭证和 AI 页面。
- 园方屏：三维沙盘为主体，外围指标疏密有序；预警能定位对应区域。
- 游客屏：大触控目标、设施查询、镜头过渡及二维码交接。
- 前线处置端：明确待办、开始处理与完成反馈，处理人和结果记录可追溯。
- 后台：统一表格、筛选、抽屉详情、表单及操作反馈。

所有可见交互均有可解释结果。重点覆盖加载、空数据、输入错误、成功、失败和断线状态；按钮不能长期停留在“建设中”。

数据变化、沙盘颜色、预警卡片、提示消息和声音形成统一反馈。AI 展示加载与流式回答，不添加虚构的模型推理过程。

同一景点、设施和路线在手机、双大屏和后台使用相同名称、图标及状态颜色。清爽布局不等于减少内容：通过点位详情、图层、抽屉和状态卡片分层展示，避免把所有指标同时挤在首页。

### 4.2 独立入口与容器

保留五个子域名：

| 子域名示例 | 终端 | 主要用途 |
|---|---|---|
| `m.example.com` | 手机游客端 | 个人服务、二维导览、预约、问答及聊天 |
| `ops.example.com` | 园方大屏 | 三维运营沙盘、指标、预警与调度结果 |
| `visitor.example.com` | 游客触控屏 | 三维公共导览、景点及设施查询 |
| `admin.example.com` | 后台及演示控制 | 管理操作、场景切换、步骤跳转和重置 |
| `gate.example.com`（历史占位） | 前线人员处置终端 | 开始处理、完成反馈及处置记录 |

五个前端独立构建和部署，共用组件与视觉资产；Ingress 将各站的接口和 WebSocket 转发到同一个后端。`example.com` 为文档占位域名，实际部署使用可控制的域名与 HTTPS。

Kubernetes 保留最小配置：

- 五个前端 Deployment 和 Service。
- 一个后端 Deployment，固定单副本，使用 Recreate 更新策略。
- SQLite 持久卷。
- Ingress 子域名路由、HTTPS 和基础探针。
- 本地 kind 运行，Docker Compose 作为备用。

集群扩展演示只操作无状态前端 Pod：扩副本、删除 Pod、观察重建。通过实际 Kubernetes 状态或终端命令展示，不建设集群监控采集平台，不宣称后端高可用。

SQLite 持久卷不代表跨节点高可用存储；后端演示期间保持单实例和固定可访问的数据卷，不对后端执行多副本或跨节点故障迁移表演。

### 4.3 现场准备

- 手机、双大屏、后台和核销电脑能够访问同一后端。
- 配置各子域名的解析、HTTPS 和对应的入口二维码。
- 后续前线处置设备验证登录、任务读取和完成反馈；本轮由 Mock 快照展示状态。
- 云端与现场备用使用同版本程序和初始场景，各自独立运行，不同步业务数据。
- 现场备用提前准备可由手机访问的局域网解析与可信 HTTPS；不将联网隧道作为断网备用的必要条件。
- LLM 无法访问时保留明确错误提示、重试和预置知识阅读入口；其他功能在现场后端可达时继续运行。

## 五、演示与验收

### 5.1 主线演示

保留约 10 分钟主线：

**手机预约 → 人脸识别入园（后续接入）→ 大屏人数变化 → 路线推荐 → 扫码介绍与真实问答 → 多人聊天 → 触发告警 → 人工安排现场工作 → 前线开始处理 → 完成反馈 → 园方告警归档。**

本轮园方原型通过手动切换完整 Mock 快照展示，不执行上述跨端服务。

主线按操作者推进，避免将下一步骤绑定到 LLM 必须在固定秒数内返回。停车紧张、厕所维修、降雨与 Kubernetes 前端 Pod 重建作为可选扩展演示。

所有主线步骤可以从控制台恢复对应的预置状态，也可以从预约开始完整操作。自由操作重点覆盖换时段、改期、取消、换偏好、查看其他点位和切换聊天室，不要求任意复杂业务组合都形成真实运营系统级处理。

### 5.2 实现顺序

1. 确定景区内容、视觉规范和五端关键页面。
2. 完成高保真前端及本地样例交互。
3. 接入轻后端，使订单、扫码、聊天和调度跨端联动。
4. 接入真实问答，完善场景控制和路线模板。
5. 配置容器、子域名和轻量 Kubernetes。
6. 集中打磨动画、反馈、异常表现及现场排练。

开发期限与团队人数尚未指定，按上述依赖顺序安排，不沿用 V1.1 的生产级后端建设阶段。

### 5.3 验收标准

验收围绕展示效果和逻辑闭环：

- 五个终端独立访问，页面无明显错位、遮挡和未完成入口。
- 换时段、换路线偏好、取消订单等常见自由操作仍能成立。
- 前线开始、完成及园方只读更新口径明确；人脸识别验收在后续接入阶段制定。
- 关键操作在正常网络下 3 秒内影响相关终端。
- 同一场景下手机、沙盘、图表和预警一致。
- 两个账号能跨设备聊天，撤回和禁言有效。
- 断线有提示，重连恢复当前状态；重置后可以再次完整演示。
- 在实际演示设备上连续运行 30 分钟，无明显卡顿或界面故障。
- 后台关键操作能够在相应终端验证效果；普通管理保存后可重新查询。
- 地图关闭点位后不推荐含该点位的路线模板，无匹配方案有清楚提示。
- 问答成功展示实际模型回答及对应知识来源，失败时不会伪装成成功。
- Kubernetes 前端副本调整与重建能通过真实状态验证，后端保持单实例。

取消原定 3,000 名个体仿真、复杂并发压测、跨副本事务及数据库故障恢复验收。文档清楚区分真实功能、规则模拟和预设内容，将投入集中到用户能看到和操作到的部分。
