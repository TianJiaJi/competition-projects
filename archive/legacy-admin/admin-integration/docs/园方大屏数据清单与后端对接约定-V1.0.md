# 园方大屏数据清单与后端对接约定 V1.0

归档日期：2026-09-12。适用应用：`apps/ops`。本文依据已实现前端整理，供后端建模、接口适配和联调使用；当前没有真实请求、告警引擎或持久化服务。页面移除了 Mock 提示，但数据仍是固定 Mock。

## 1. 交付物与阅读顺序

1. 本文：展示字段、单位、计算口径、状态变化和待对接差异。
2. [归档目录](archive/园方大屏-2026-09-12/README.md)：六种完整运行场景、对应统计结果、静态区域与点位、校验清单。
3. [TypeScript 类型](../packages/contracts/src/index.ts)：`PublicSnapshot`、`OpsPrototypeSnapshot`、`OpsAlert`、`OpsHandlingRecord`、`OpsFeedEvent`、`OpsAlertStatistics`。
4. [Mock 生成器](../apps/ops/src/mock.ts)、[处置统计](../apps/ops/src/alert-stats.ts)：当前可执行口径；基础设施数值还来自 `packages/client`，静态对象来自 `packages/scenic/src/data.ts`。
5. [接口文档](智慧景区接口文档-V1.0.md)与 [OpenAPI](openapi/scenic-api-v1.0.yaml)：历史接口基线。`OpsPrototype*` 是展示契约，**没有绑定生产路径**，不能把旧 `/ops/snapshot` 的响应直接送进当前应用。

## 2. 数据边界与通用约定

- 园方只读监控、人工安排调度；前线反馈开始及完成。此屏不提供派单、确认告警或结案写接口。
- 人脸识别入园替代旧扫码入园；本轮只消费累计人数，不需要人脸照片、特征或身份明细。
- 业务时区 `Asia/Shanghai`。业务时间、采样时间、事件时间使用带时区 ISO 8601，例如 `2026-09-12T14:30:00+08:00`；不能使用浏览器当前时间替代业务时间。
- 所有数量使用数值型原始值；人数、车位、事件数为非负整数，分钟、风速可有小数。千分位、百分号和单位由前端格式化；告警 `metric` 是例外，当前是带单位的展示摘要。
- `public.points`、`public.regions` 是按稳定 ID 索引的字典，不是数组。当前页面直接读取全部区域、停车场、索道与卫生间，不能只传变化对象当作完整快照。
- 公共类型允许若干数值为 null，但当前大屏只验收完整数据，仍有非空断言和固定文字。**null、缺键、断线、跨日不能直接上线套用此原型**，接入时需增加适配、数据质量和旧数据保留策略；不可把未知值默认为 0。
- `id`、`label` 是本地运行场景标识；正式响应不需要把场景名称当成业务实体。`public.revision` 是公共快照版本，建议正式响应再提供全量快照版本、生成时间及运行实例标识，统一绑定指标与事件。本条为后续建议，尚未实现。

## 4. 区域与热力

静态 `Region` 包含 id、name、x/z、radius、capacity；其中 x/z/radius 是模型局部坐标，不是经纬度。动态 `RegionState` 包含 availability、load、count、可选 reason。

| ID | 区域 | 参考承载（人） | 默认在园（人） | 可用性 / 热力 |
| --- | --- | ---: | ---: | --- |
| Z0 | 入口服务区 | 1000 | 380 | open / quiet |
| Z1 | 溪谷区 | 1100 | 492 | open / quiet |
| Z2 | 竹林区 | 1100 | 635 | open / quiet |
| Z3 | 峡谷观景区 | 1000 | 547 | open / quiet |
| Z4 | 山顶观景区 | 1300 | 1268 | open / busy |
| Z5 | 湖畔游览区 | 1300 | 0 | closed / unknown；区域养护 |
| Z6 | 林间休息区 | 1000 | 303 | open / quiet |
| Z7 | 瀑布游览区 | 1000 | 640 | open / moderate |
| Z8 | 公共通行区 | 2500 | 1196 | open / quiet |

- 区域人数合计为 5,461；九区域参考承载合计为 11,300，**不等于全园运营上限 10,000**，不可互相替代。
- 承载率=count/capacity；列表降序排列，显示一位小数。当前 Mock：开放区域 `<60% quiet`、`60%–<85% moderate`、`≥85% busy`。关闭或维修保持独立可用性，不视为“空闲”。
- 公共热力算法读取 `load` 而非直接按人数线性上色：quiet/moderate/busy 对应内部权重 .12/.6/.98，按区域距离混合；关闭区域灰化。因此后端提供的 count、capacity、load 必须相互一致。
- 告警触发并非热力等级自动等价：当前 Z4 示例要求超过 85% 持续 2 分钟；具体引擎阈值、持续窗口和恢复回差需单独配置，不从展示文案解析。
- 人数标签、相机角度和引导动画是前端表现，不需要后端给屏幕坐标。九个标签绑定固定模型锚点；Z8 在湖中央，Z4 稍抬高，详情时隐藏。

## 5. 设施明细

可用性统一为 `open / closed / maintenance / unknown`，负载为 `quiet / moderate / busy / unknown`。安全设施对应“可用 / 不可用 / 状态未知”，定期检修待办本身不改变可用性。

### 停车

`public.points[p1|p2|p3]`：availability、load、parkingCapacity、parkingFree；已用=容量−余位。p1/p2/p3 依次为一、二、三号停车场。

| ID | 总泊位 | 已用 | 余位 |
| --- | ---: | ---: | ---: |
| p1 | 700 | 572 | 128 |
| p2 | 500 | 404 | 96 |
| p3 | 300 | 236 | 64 |
| 合计 | 1500 | 1212 | 288 |

Mock 停车负载按已用比例 `<70% quiet`、`70%–<90% moderate`、`≥90% busy`。不能把区域热力阈值套到停车场。

### 索道

`public.points.upper/lower.cable`：**upper 是上站下行，lower 是下站上行**，不能按 ID 英文猜乘坐方向。

| 字段 | 单位 | 上站 upper / 下站 lower |
| --- | --- | --- |
| direction | up / down | down / up |
| queueCount | 人 | 112 / 48 |
| waitMinutes | 分钟 | 6 / 2.8；服务侧估算，前端不重新推算 |
| inTransit | 人 | 36 / 24 |
| cabinSeats / cabinCount | 人每厢 / 厢 | 8 / 40 |
| totalCapacity / directionCapacity | 人 | 320 / 160 |
| dispatchSeconds / travelMinutes | 秒 / 分钟 | 24 / 8 |
| capacityPerMinute | 人每分钟 | 20 |
| opensAt / closesAt | HH:mm | 08:00 / 18:30 |

大屏显示前两项，其他字段保留供公共设施契约和后续明细使用。横条目前共同以 15 分钟为满刻度，超过 15 分钟的表现需接入时调整。

### 卫生间

t1–t6 的 `PointState.restroom` 含总计和 female（女厕）、male（男厕厕位）、maleUrinals（小便池）、accessible（无障碍）四分项；每层均为 totalStalls、occupiedStalls、availableStalls、queueCount，单位个/人。完整数值见 JSON。

默认 t1/t2/t4/t6 开放、t3 维修、t5 关闭：分段条为 **4 / 1 / 1 处**。最繁忙点位只在开放卫生间中选择，先按排队人数降序，再按占用/总量降序；默认 t2 溪谷卫生间，排队 0 人。

容量保留是物理设施数量；关闭和维修时可用数可以为 0，不能强制所有状态都满足“总量=占用+可用”。只对全部服务正常的分项使用该等式。当前类型没有分项暂停字段，管理员后台提出的分项暂停需扩展契约后对接。

### 安全设施与其他点位

复用公共六类共 15 处安全设施：aed、first-aid、help、lifebuoy、extinguisher、shelter。完整 ID、名称、归属、nodeId 见静态 JSON。默认 fire-bamboo 与 help-creek 为 maintenance，aed-summit 保持 open，虽有例行检修提醒仍显示可用。不设常驻安全统计面板，异常进入告警。保洁可挂在 market 等商业点位，不需要新增模型。

## 6. 告警、处理记录与事件流

| OpsAlert 字段 | 必填 | 说明 |
| --- | --- | --- |
| id | 是 | 稳定事件编号；恢复后再次异常产生新编号 |
| anchorId | 是 | 公共点位 ID 或 `region-`+区域 ID，例如 help-creek / region-Z4 |
| regionId | 是 | Z0–Z8；必须与锚点归属一致 |
| category | 是 | crowd、parking、cable、restroom、equipment、help、cleaning、inspection |
| severity | 是 | reminder 提醒、important 重要、critical 紧急；由事件显式提供 |
| status | 是 | pending 待处理、processing 处理中、resolved 已处理 |
| title / location | 是 | 标题与地点显示名 |
| reason | 是 | 原因；可包含持续时间、触发条件 |
| metric | 是 | 监测摘要，明确触发时或当前值及单位；不是可解析的结构化测量 |
| startedAt | 是 | **当前字段名表示告警发生时间，不是开始处理时间** |
| records | 是 | 至少一条 created；时间升序，不能补虚构处理记录 |
| previousAlertId | 否 | 复发事件关联上一轮；无关联时省略 |

`OpsHandlingRecord`：at（ISO 时间）、kind（created/started/completed）、actor（处理人或来源显示名）、text（过程/结果）。开始处理时间从 `kind=started` 读取；完成时间从 `kind=completed` 读取。未开始、未完成时不填空字符串、横线或未来记录。生产建模建议使用 occurredAt、handlingStartedAt、resolvedAt 和稳定 recordId/actorId，通过适配层映射当前结构；这些字段目前未加入类型或接口。

`OpsFeedEvent`：id、alertId、at、kind、title、text、severity 均必填；由对应处理记录产生，text 当前为“actor：text”。Mock ID 为 alertId+记录下标；生产需稳定记录 ID，防止补录或排序后重复提示。时间倒序，同时间用 ID 稳定排序。事件流不随告警列表筛选；旧消息阅读时保留位置，新消息提示返回顶部，不弹窗、不自动抢镜头、默认静音。

行为要求：

- 未完成列表=全园 pending+processing，紧急优先，其次 important/reminder，同级发生时间最新优先、ID 兜底。
- 级别、类别、处理状态筛选同步影响当前点位；全园指标和今日处置统计不变。历史查看展示 resolved；现有地图仍显示按级别/类别过滤的未完成点位。
- 同 anchorId 未完成事件合并，数量取该点事件数、颜色取最高级别；默认 7 条合并为 6 个点，help-creek 为 2 条。
- 人工完成后从当前列表移除，历史、点位计数、事件流同步更新。同点还有未完成事件则保留图标。
- 完成不自动降低客流、不自动恢复设备；数值恢复不自动结案。同轮持续异常不重复创建，恢复再超限才是新事件，定期检修按新周期创建。
- **全园任意未完成 critical 存在时红色水墨持续显示**，不受详情开关、过滤或历史查看影响。最后一条 critical 人工完成后淡出。
- 详情可选择历史事件，安全设施状态仍读取当前公共快照，并非事件发生时状态；若需要历史状态追溯，应增加事件时测量/设备快照。

## 7. 派生指标与时间口径

| 指标 | 当前计算 |
| --- | --- |
| 全园承载率 | visitors / 10000，保留一位百分数 |
| 累计离园 | checkedInToday − visitors；只适用于开园在园数为 0、统计口径一致的当前演示 |
| 未完成 / 紧急数 | 所有 alerts 中 status != resolved / 再筛 severity=critical |
| 分时在园 | 08:00 0、09:00 1460、10:00 2780、11:00 3920、12:00 4720、13:00 5180、14:00 5390、14:30 5461；当前点等于实时在园 |
| 今日事件总数及环图 | 当日发生且发生时间不晚于业务时刻的 alerts，按当前状态计数 |
| 平均响应 | 已有 started 记录事件的（首次开始处理−发生），取算术平均，分钟保留一位小数 |
| 平均处理 | 已有 started 和 completed 事件的（首次完成−首次开始），取算术平均，分钟保留一位小数 |
| 新增/完成双折线 | 08:00 起每小时桶；发生时间计新增，完成时间计完成；最后一桶仅到业务时刻，无未来数据 |

默认今日 **24 条=5 待处理+2 处理中+17 已处理**，响应 **3.5 分钟**，处理 **13.2 分钟**。分时在园当前 y 轴最大 6000；区域条最大 100%，接入真实超量数据前需扩展图表范围。

必须明确的生产差异：当前统计先筛“今天发生”的事件，因而昨天发生今天完成的事件不进入今日完成趋势；早于 08:00 的同日事件被计入首桶。样例没有跨日和开园前事件，这不是已验证的生产统计规则。建议生产独立统计今日新增（按发生时间）、今日完成（按完成时间）、全园未完成（跨日保留），环图是否采用当日事件集合另行确定。当前响应均值无样本时返回 0，真实接入应区分“没有样本”和实际 0 分钟。

## 8. 后端接入能力与实施顺序

以下是所需读取能力，**不是新增已实现路由**：

| 能力 | 输入 / 输出要求 |
| --- | --- |
| 完整园方快照 | 园区/运行上下文、版本；返回指标、天气、全区域与设施字典、业务/采样时间 |
| 在园时间序列 | 日期、截至时间、采样粒度；只返回已发生样本，补当前点 |
| 当前告警与详情 | 全园跨日未完成集合、稳定 ID、完整处理记录、位置和实际设备状态 |
| 今日统计 / 历史查询 | 全量统计不受分页与筛选影响；当前实现需要完整当日事件，分页后不能仅对当前页计算环图 |
| 事件增量 | 游标、稳定事件 ID、快照版本；重连补拉、去重、乱序保护，不能漏掉人工完成 |

建议先用完整归档 JSON 对接只读适配层，再引入版本化全量读取，最后接入增量推送。全量替换应原子更新，避免 KPI、图表、列表各自更新出短暂矛盾。稳定状态更新保留筛选、阅读位置、自转开关与当前详情；被删除或完成的选中事件如何留在历史详情应明确处理。当前运行场景切换会主动关闭详情，不能直接拿该演示切换函数当生产订阅逻辑。

正式联调前需一起更新接口文档与 OpenAPI：旧状态 acknowledged/recovered、旧数组型公共数据、旧派单与自动恢复流程均不可直接复用；生产鉴权、运行隔离、分页、错误、断线恢复仍按正式契约设计。本次只归档与列差异，不实现后端或新路由。

## 9. 六种场景验收基线

所有场景累计入园 8236、实时在园 5461、余位 288。场景独立生成，不能视为真实时间连续回放。

| 场景 ID | 业务时刻 | 待处理 / 处理中 / 已处理 | 未完成 | Z4 人数 | 紧急水墨 |
| --- | --- | --- | ---: | ---: | --- |
| alerts | 14:30 | 5 / 2 / 17 | 7 | 1268 | 有 |
| normal | 14:30 | 0 / 0 / 24 | 0 | 860 | 无 |
| processing | 14:35 | 4 / 3 / 17 | 7 | 1268 | 有 |
| completed | 14:45 | 4 / 2 / 18 | 6 | 860 | 有 |
| still-high | 14:45 | 4 / 2 / 18 | 6 | 1268 | 有 |
| recurrence | 15:10 | 5 / 2 / 18 | 7 | 1268 | 有 |

normal/completed 将 Z4 减少的 408 人转入 Z8，保持全园守恒；recurrence 新建 A-237，关联 A-230。completed 只完成客流事件，不代表全园所有紧急事件已完成。

联调检查：人数求和、停车求和、趋势末点、枚举/ID 引用、发生≤开始≤完成≤业务时刻、状态与记录一致、趋势合计与统计一致、同点聚合与筛选、人工完成与复发、紧急全园状态不受筛选影响。分别在 1920×1080、1440×900 检查深浅主题、专注返回、首次加载、减少动态效果和三维失败。真实数据接入时另补跨日、乱序、无样本、超量、断线和设备分项暂停样例。
