## 使用顺序与就绪边界

先核对[极简确认清单](部署前极简确认清单.md)，确认集群、持久卷、证书、镜像、SakuraFrp 隧道、DNS 和 VPS 凭据可用，再按 PG 迁移材料将本机已迁移数据导入目标主库。内网 SSH 口令此前曾以 Base64 形式暴露，必须先轮换；仅使用轮换后的口令或恢复可信密钥，不再使用旧口令。服务器登录资料只保存在本机忽略文件，仓库只保留空白模板。

当前后端使用 pg 连接 PostgreSQL 17，普通启动会检查 schema，不会建 schema、播种账号或重置运行。本机 PG scenic_local 已在 2026-09-24 生成权限为 600 的一致性快照，原 SQLite 数据仍保留；本机导入、并发幂等、配额、回滚、QA 中断恢复和六端联调已有记录，详见[本地实施记录](implementation/PG迁移与本地联调-2026-09-13.md)。远端实际验收见单入口实施单。

## 拓扑与参数

本轮复用现有内网 K8s 和香港 VPS；不部署旧方案中的第二个公网入口、PG 备库或新主机。内网两节点的旧清单仍须在发布前重新核实。

```text
六端浏览器 → 六域名 → 香港 VPS Caddy（HTTPS / AliDNS DNS-01）
                         ↓ SakuraFrp 公网 TCP 转发端点
内网 K8s frpc ───────────┘
        ↓ Ingress HTTP NodePort 31101
六个前端 + 单活动 Node.js 后端
                         ↓ TLS
                PostgreSQL 17 单主库 + 持久 PVC
```

六域名：`m/ops/visitor/admin/gate/demo.starhusk.com`；六个静态前端可独立重建，但请求必须进入同一后端。手机端部署 H5，不把小程序产物当静态网站。Compose 用 `mobile/ops/visitor/admin/gate/demo.localhost:8080`，只绑定本机回环地址，不供生产入口转发。

现有集群资料是 2026-09-11 快照：node1 172.25.5.19、node2 172.25.5.20，K8s 1.27.6、containerd 1.7.27、nginx Ingress、HTTP NodePort 31101。发布前重新核验节点、路由、空间与 Ingress Service。旧记录根分区约 7.1/15 GiB 空闲，不能据此推定主库卷或七个镜像可落盘。

内网覆盖层请求 10Gi PVC，使用集群默认 StorageClass 动态供给。应用前必须确认默认 StorageClass 存在、容量足够，并把新建 PV 的回收策略设为 Retain；如集群没有可用 StorageClass，先核定实际磁盘、节点和目录再配置 local PV，不可编造路径。正常升级不删除 PVC。

PostgreSQL 管理员与 scenic_app 密码分别放在 scenic-postgres-secrets 私有 Secret；后端的 DATABASE_URL 使用 scenic_app，DeepSeek Key 也从私有 Secret 注入。PG 服务端 TLS Secret 必须包含 tls.crt 和 tls.key，服务端证书 SAN 包含 scenic-pg-primary.scenic-demo.svc；后端单独挂载 ca.crt 并设置 PG_CA_FILE=/run/secrets/postgres/ca.crt。生产连接串不带 ssl 查询参数，也不设置 PG_ALLOW_INSECURE。

## 构建与发布版本

以下命令从仓库根目录执行，要求 Docker Engine + Buildx + Compose v2；本机 ARM64，服务器通常 AMD64。所有镜像用同一不可复用的发布标签，正式发布另记录基础镜像和产物摘要、源码提交及未提交补丁快照。

```sh
export RELEASE_TAG=20260913-pg-01
for app in mobile ops visitor admin gate demo; do
  docker buildx build --platform linux/amd64 --load \
    -f infra/images/frontend.Dockerfile --build-arg APP="$app" \
    -t "scenic/$app:$RELEASE_TAG" .
done
docker buildx build --platform linux/amd64 --load \
  -f infra/images/server.Dockerfile -t "scenic/server:$RELEASE_TAG" .
```

本机联调改用 `linux/arm64`；跨架构使用不同归档文件名，不能把 ARM 镜像误导入 AMD 节点。前端路径：mobile 为 `dist/build/h5`，其余为 `dist`。构建上下文只应包含可发布资料，`.dockerignore` 排除环境文件、数据库、私有登录表及本地产物。正式镜像不包含登记表或密码。

初期不建立镜像仓库：用 `docker save -o <发布包.tar> <七个镜像名>` 导出，计算 SHA-256 后经已核验的 SSH 传输；目标每个允许调度的节点执行 `sudo ctr -n k8s.io images import <发布包.tar>`，确认架构、版本和可用性。不要在控制面堆积构建缓存。将 overlay 七个 `newTag` 同步改为发布标签；保留前一版本供应用回滚，回滚前验证 schema 兼容性。

## Compose 联调

将 `.env.example` 复制到 `infra/compose/.env` 并填写独立测试凭据，已有文件不覆盖。示例密码只接受足够长的 URL 安全字符；特殊字符需要连接串编码。`POSTGRES_PASSWORD` 为迁移管理员密码，`APP_POSTGRES_PASSWORD` 为独立 scenic_app 业务密码。新卷初始化创建 scenic_app，migrate 命令授予业务表权限；现有卷不会重新执行初始化脚本，若角色不存在，应先由管理员创建该角色，不能删除卷补建。

```sh
docker compose --env-file infra/compose/.env -f infra/compose/compose.yaml config --quiet
docker compose --env-file infra/compose/.env -f infra/compose/compose.yaml build
docker compose --env-file infra/compose/.env -f infra/compose/compose.yaml up -d postgres
docker compose --env-file infra/compose/.env -f infra/compose/compose.yaml --profile tools run --rm migrate
# 下一节完成导入、核验与备份后再启动。
docker compose --env-file infra/compose/.env -f infra/compose/compose.yaml up -d
```

数据库不映射宿主机端口，持久卷 `pg-data` 独立于正式库。`down` 保留数据，不执行 `down -v` 作为普通重启。访问 `http://mobile.localhost:8080` 等六端；本地域名解析异常时补齐 hosts 指向 127.0.0.1。更改 HTTP_PORT 时必须同步 Caddy 站点端口和 ALLOWED_ORIGINS。

## 数据导入与开放闸门

1. 以活动进程打开的文件为准登记两库实际路径、大小、表数、集合数和应用版本。停止原后端、watch 父进程、仿真与 AI，确认没有其他写者；通过 SQLite backup API 创建一致性备份，不能在线只复制主文件。
2. 先在隔离目标演练。使用迁移管理员 DATABASE_URL 执行 `node apps/server/scripts/migrate.ts`，再执行 `node apps/server/scripts/import-sqlite.ts <平台备份绝对路径> <QA备份绝对路径> <报告绝对路径>`。导入要求空业务表；同源重跑只返回已导入，不覆盖新业务。非法 JSON、约束冲突或校验差异整批回滚。
3. Compose 内用 migrate 服务的管理员环境执行导入，覆盖 entrypoint 为 node，脚本路径为 `/app/apps/server/scripts/import-sqlite.ts`。备份目录只读挂载；报告目录单独可写挂载，保证退出容器后报告仍保留。不要将管理员凭据注入 server。
4. 核对报告每个表及集合、标准化内容校验和、原账号和会话、幂等结果、最大 seq 和 selectedRunId；历史检查点修复和未完成 QA 中断数量必须可追溯。静态资料校验和随发布归档。
5. 建立 PG 基线备份并在隔离目标恢复。切换业务账号启动一个候选后端，核对六端同运行、受控写入、断线重连及版本冲突。普通启动不建新的展示运行；生产禁止运行 demo seed。
6. 开放前失败可恢复原应用和成套 SQLite 备份；开放后已有新写入，必须先停写、备份 PG、登记增量，再决定前向修复或回迁，不能直接回旧 SQLite 接受写入。

全新测试库无历史数据时，可在本地非生产环境显式执行 `SCENIC_SEED_DEMO=1 pnpm --filter @scenic/server db:seed-demo`。它只补缺，使用弱密码演示账号，禁止在生产执行。

## K8s 发布（前置条件全部完成后）

先渲染检查，不需要集群连接：

```sh
kubectl kustomize infra/k8s/overlays/intranet > /tmp/scenic-intranet.yaml
```

检查没有示例节点/路径、镜像版本一致、后端只有一个活动实例目标。基础模板保留 0 副本，直到 PG 迁移、数据库工作负载与主备验收完成，再将 server 的 replicas 明确更新为 1。主库 Service 当前没有可选中的 PG Pod，不能作为数据库可用证明。

私有 Secret 文件格式参考 `infra/k8s/server-secret.env.example`，实际文件放仓库外并限制权限。由部署人员在确认的 `scenic-demo` 命名空间创建 `scenic-server-secrets`，例如使用 `kubectl create secret generic ... --from-env-file=<私有文件>`；不要把凭据放命令参数或提交生成的 Secret YAML。迁移管理员凭据不注入业务 Pod。另创建 `scenic-postgres-ca` Secret，键名 `ca.crt`，挂载路径已在 server 模板配置；证书 SAN 必须匹配连接串中的主库 Service 名。

核对 kube context 后先做服务端 dry-run，检查旧集群 API、资源配额和 admission，再应用经过审核的渲染结果。PG 主备工作负载属于后续实施，必须接入预留卷与唯一主库 Service；本轮材料不会自动创建它们。`/api/v1/health/ready` 检查 PG、schema、可写主库和选中运行，失败返回 503；`/api/v1/health/live` 只检查进程。K8s 探针已分别配置这两个路径，不能把模型故障当进程死亡。

应用发布采用 Recreate 并有短暂停机。节点失联时执行隔离规则，不用强删 Pod 假装旧进程已停止。原有命名空间、Ingress 控制器、旧 ngrok 及 VPS 既有应用不改动。

## 公网入口与穿透对接

香港 Compose 只占用 80/443，保留证书卷。填写 `.env` 后先创建/接入最终穿透适配器的外部 Docker 网络，`TUNNEL_UPSTREAM` 必须是 Caddy 容器可访问的私有端点，例如 `tunnel-adapter:18080`。容器内 127.0.0.1 不是宿主机；若最终穿透落地到宿主机回环端口，需要明确网络适配，不能原样套用该示例。不得公开穿透落地业务端口。

备用 VPS `92.5.152.95` 已有 `/opt/edge-caddy` 和 `edge-public`。只将备用片段合入现有 Caddyfile，并为现有容器注入 `SCENIC_TUNNEL_UPSTREAM`、接入适配器网络；由该网关继续统一占用 80/443。此轮不修改该服务器或 my_server。两边先验证配置、证书和回程链路，再开放域名；切换证书准备要求见同步需求。

穿透验收接口：由内网主动建立到两个公网入口的独立连接，均转发至当前内网 Ingress；保留原始 Host；认证加密；支持 WS、AI SSE/流式、不缓冲、长连接和自动重连。隧道实现与认证端口仍待定，不部署 frps/frpc。

Caddy 明确传递外部 HTTPS 信息，但现有 ingress-nginx 是否正确接受转发头必须实测。不可为本项目盲目开启全局 `use-forwarded-headers` 而影响旧应用；如需调整，仅信任核定代理来源，或使用经验证的专用入口路径。该项未完成前不能宣称后端已识别外部 HTTPS。Ingress 不强制重定向到不存在的集群 TLS 证书，公网 TLS 在入口终止。
