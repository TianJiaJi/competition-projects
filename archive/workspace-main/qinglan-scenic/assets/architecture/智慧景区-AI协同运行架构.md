# 智慧景区 AI 协同运行架构

## 一、系统组成与职责

系统由现有业务系统和 AI 功能两部分组成。现有系统提供数据、业务接口和操作终端；智能体负责理解信息、分析问题、生成建议，并调用业务接口完成相应操作。

| 部分 | 模块 | 主要职责 |
| --- | --- | --- |
| 现有系统 | 业务数据 | 提供客流、设施状态、预约信息、游客公开内容及处理记录 |
| 现有系统 | 业务服务 | 提供数据查询、通知发布、任务管理、内容处置和结果回写接口 |
| 现有系统 | 交互与处置终端 | 游客端承接提问和回答；园方大屏展示告警；管理后台支持安排、复核与管理；前线人员反馈处理结果 |
| AI 功能 | 运营监测 Agent | 调用检测工具识别异常，结合运行数据研判风险，推送告警、生成处置建议并跟踪处理结果 |
| AI 功能 | 游客服务 Agent | 检索景区知识、查询当前状态，提供知识库问答、景点讲解和游览建议 |
| AI 功能 | 内容审核 Agent | 审核游客公开内容，调用接口处理明确违规内容，将疑似问题提交人工复核 |

## 二、运营监测与人工处置闭环

运行数据 → 异常检测 → 智能研判 → 告警与建议 → 人工处置 → 结果回写 → 持续监测

| 步骤 | 执行主体 | 业务动作 | 输出与去向 |
| --- | --- | --- | --- |
| 1. 获取运行数据 | 现有系统 | 汇集客流、设施状态、预约及历史处理记录 | 向运营监测 Agent 提供当前状态和相关记录 |
| 2. 检测异常 | 运营监测 Agent 调用检测工具 | 依据阈值、持续时间和状态变化识别拥堵、设施异常等事件 | 将异常指标及事件信息送入研判环节 |
| 3. 研判风险 | 运营监测 Agent | 结合当前数据、历史记录和处置预案，判断影响范围与风险等级 | 生成告警内容及处置建议 |
| 4. 推送告警 | Agent 发起调用，业务服务执行 | 调用通知接口发布告警与建议，记录事件 | 告警送达园方大屏和相关人员 |
| 5. 安排与执行 | 管理人员、前线人员 | 人工确定处理安排，开展现场处置，更新任务进度 | 形成处理状态、执行说明与处理结果 |
| 6. 回写结果 | 现有系统 | 保存人员反馈及事件处理记录，更新任务状态 | 向运营监测 Agent 提供可查询的处理结果 |
| 7. 持续跟踪 | 运营监测 Agent | 查询处理结果，结合后续运行数据观察异常是否缓解 | 未缓解时继续提醒并补充建议；已缓解时记录恢复情况，继续监测 |

例如：系统发现某区域客流持续偏高，智能体结合区域容量和现场状态研判风险，向园方及相关人员推送告警与分流建议。管理人员安排前线人员引导，前线人员提交处理结果；智能体继续查看该区域客流，跟踪是否恢复正常。

告警自动推送，人员安排与现场执行由人工完成。任务完成状态与实际运行状态分别记录，人员提交“已处理”不等于现场指标已经恢复正常。内部告警面向园方和相关人员；面向游客的提示通过游客公告等业务渠道发布。

## 三、游客问答服务闭环

游客提问 → 理解需求 → 检索知识与查询状态 → 生成回答 → 返回游客 → 继续追问

| 步骤 | 执行主体 | 业务动作 | 输出与去向 |
| --- | --- | --- | --- |
| 1. 提交问题 | 游客端 | 接收游客问题及当前会话信息 | 将问题提交给游客服务 Agent |
| 2. 获取依据 | 游客服务 Agent | 按问题检索景区资料、服务规则；涉及开放、排队等动态信息时调用状态查询接口 | 获得回答所需的知识和当前业务信息 |
| 3. 组织回答 | 游客服务 Agent | 结合检索结果、业务状态和会话上下文，生成讲解或游览建议 | 将回答返回游客端 |
| 4. 展示与追问 | 游客端与游客服务 Agent | 展示回答，记录本次会话；游客追问时沿用上下文 | 形成连续问答，必要时重新查询状态或检索知识 |

例如：游客询问“现在适合去哪个景点”，智能体结合景点介绍、开放情况和当前客流给出建议。游客继续询问路线时，智能体结合前文需求继续回答。

营业时间、开放状态、预约规则等信息以业务数据和正式知识为依据。资料缺失或状态无法查询时，应说明不确定性或提供人工咨询指引。会话记录不自动写入公共知识库。

## 四、公开内容审核闭环

游客发布内容 → 智能审核 → 分类处理 → 结果回写 → 相关终端同步

| 审核结果 | 后续动作 | 执行主体 | 结果回写 |
| --- | --- | --- | --- |
| 内容正常 | 保留内容，包括正常差评、投诉和合理反馈 | 内容审核 Agent 记录判定，业务系统保留内容 | 保存审核结果与依据 |
| 明确违规 | 调用内容处置接口，按规则处理违规内容 | Agent 发起调用，业务服务执行 | 根据接口实际执行结果记录处理状态，并同步相关终端 |
| 疑似违规 | 提交人工复核，由管理员决定是否处理 | Agent 提交复核任务，管理员作出决定，业务服务执行 | 保存复核决定、处理理由及执行结果 |

例如：游客发布公开文字后，智能体结合内容和上下文进行审核。明确违规的内容由业务接口执行处置；无法确定的问题交管理员复核。处理结果回写业务系统，供后台查看，并同步到相关终端。

审核结论和执行结果分别记录。接口调用失败时保留失败状态并进入重试或人工处理流程，不将未执行成功的操作标记为已完成。

## 五、三个智能体共用的支撑能力

| 支撑能力 | 提供的能力 | 在业务中的作用 |
| --- | --- | --- |
| DeepSeek 大模型 | 语义理解、推理与文本生成 | 支撑风险研判、问答生成和内容审核 |
| 知识库 / RAG | 检索景区资料、服务规则与处置预案 | 为回答、研判和建议提供依据 |
| 业务工具调用 | 阈值检测、状态查询、通知发布、任务处理和内容处置 | 让智能体获取业务信息、发起操作并读取执行结果 |
| 业务记录与反馈 | 保存事件、会话、审核和处置记录 | 支撑进度跟踪、后续查询和人工复核 |

现有系统技术栈简要表示为 Vue 3、Node.js、PostgreSQL；AI 部分简要表示为 DeepSeek、知识检索 RAG 和业务工具调用。

业务结果回写用于更新状态和保留记录。需要进入正式知识库的内容，由人工整理、审核后发布，不将业务回写等同于自动更新知识库或自动训练模型。
