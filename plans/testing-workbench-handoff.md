# 智慧校园测试工作台：手动讲解式项目交付与验收

## Context
- 将现有以系统/API目录为中心的测试工作台，改为以“上游方案生成项目并交付 → 接收消息 → 新测试任务 → UI/API/专项验证 → 报告反馈”为中心的操作流程。
- 交付消息、后端工程师指派、用例生成均采用本地预制数据和可操作状态流转，不开发真实岗位通信、AI生成或远程测试调度。
- 用户补充：一切为现场讲解服务，要有可见的工作过程和联动；所有测试由演讲者逐项手动触发，不自动串行执行。只处理智慧校园，默认项目固定，启动工作台须联动启动校园项目，其他项目不做。
- 当前仅规划，获得批准前不修改代码、不安装、不启动新服务、不提交Git。

## Approach
- 增加项目交付消息及测试任务入口，任务携带方案来源、项目版本、访问入口、API材料、工程师专项要求；消息与任务通过稳定ID关联，避免重复接收重复建任务。
- 项目任务内组织“交付概览 / UI验证 / API验证 / 专项验证 / 成果报告”，保留现有API与压测能力，减少跨系统选择与管理弹窗的跳转。
- 接收、解析材料、生成用例、执行与报告都从同一份任务状态驱动，不以互不关联的静态页面冒充联动。
- 已确认：UI采用内嵌预览＋新窗口；演示通过“接收上游交付”按钮触发消息和新任务；工程师要求固定，生成的测试用例可调整。
- 默认固定为“智慧校园 / 知行校园项目”，隐藏多系统切换和其他平台发现；保留旧系统存储工具，不删除原配置，不开发其他项目流程。
- 新发现：现有发现一次接入三个平台，缺少UI地址、HTTP方法/参数/响应说明；`App.vue/resetView`直接填入全部通过的基线结果。新工作台必须改为真实的“未生成/待测试”初始状态，未点击执行不出现通过数、报告或测试曲线。
- 固定交付包含：方案摘要、项目版本、前端/后端交付人、五端页面入口、与校园预约/请假对应的API说明、后端专项指派。无需真实上游通信或用户配置文件。
- 工作台任务与人工检查持久化；测试结果保留有界快照和报告来源，存储失败时提示并退回会话。刷新恢复已有结果时显示执行时间，不伪装成新一轮执行。

### 页面与讲解路径
- **任务中心（默认首页）**：顶部显示固定校园项目、版本和交付状态；主区为任务卡/进度概况，右侧为交付消息与按操作追加的协作时间线。“接收上游交付”手动出现交付消息和新任务，展示通知、新任务数量及材料摘要；重复接收同版本只打开已有任务。
- **项目测试空间**：固定项目头部与任务编号；导航为“交付概览 / UI测试 / API测试 / 专项测试 / 压力测试 / 验收报告”，每项显示未开始、进行中、待复核、已完成状态。进入栏目或生成用例不自动执行测试。
- **交付概览**：方案→前端项目→API材料→工程师指派的链路卡，能打开对应材料；右侧保留交付与测试时间线，说明接下来操作。
- **UI测试**：左侧五端页面目录，中间真实项目内嵌预览，右侧页面检查清单；支持桌面/手机尺寸、新窗口、重新加载。检查项初始待检查，演讲者手动填写通过/需整改、备注并保存；需整改自动形成关联问题。预览加载只代表页面打开，不自动断言通过。
- **API测试**：先展示交付接口清单（方法、路径、用途、角色、请求参数、响应示例、预期结果），点击“解析API材料”展开解析记录，再点击“生成测试用例”，最后手动单项/分组/全部运行。采用固定材料映射，不接AI。运行展示用例逐项推进、断言、响应和处理流水；可停止与重测。
- **专项测试**：展示后端工程师头像/岗位、指派说明、风险点和固定验收标准。手动“生成专项用例”后可编辑参数、备注和补充人工检查点；执行仍按“准备条件→触发请求→核验结果”逐步点击。固定四项校园场景：重复提交去重、同一教室时段并发预约、跨账户/班级权限、弱网重试。用校园申请/时段/学生/教师术语，避免订单抢购文案。人工补充检查点不自动通过，不篡改工程师原始标准。
- **压力测试**：沿用并发阶梯与图表，每轮由用户点击启动，手动加压/停止可讲解；API测试完成不自动开始压测。既有阶梯按启动后既定参数推进，不自动开启下一轮或其他测试功能。
- **验收报告**：用户手动“汇总验收报告”，汇总已执行UI/API/专项/压力记录，列出未测项与问题。再手动“提交验收反馈”，追加本地回传回执；存在需整改显示“已反馈，待整改”，不冒充全量验收通过。

### 视觉与演示边界
- 浅色工作台、深蓝/青绿状态色、清楚的卡片层级和可读文字；核心按钮固定在每个测试区，处理中的局部动画、逐项进度、结果展开与时间线共同解释“正在做什么”。避免纯装饰性指标和自动跳页，支持减弱动画。
- 点击一个动作仅完成当前动作，结束后停在可讲解结果；固定材料解析/用例生成可有短暂分步进度，不自动触发任何测试。执行中锁定冲突操作，可取消，取消不记为通过。
- “重置讲解流程”二次确认后只清理本工作台草稿/记录，不清空校园业务数据、不修改项目文件。
- 项目预览是真实本地页面；API/专项/压力结果仍来自本地模型，不能宣称校园服务已实现全部幂等或并发防护。文档、详情证据来源及JSON明确区分人工观察与本地模拟；不新增真实远程通信。

### 启动可靠性
- 新增统一启动脚本；`qinglan-scenic` 的 `pnpm dev:testing`同时启动工作台5180、校园5500–5504和预约/请假服务5606，使用已有`zhixing-campus/scripts/dev.mjs`的启动清单/Windows兼容模式，避免重复启动。
- 对已占用端口核对可验证的页面标题/资源或服务健康信息，确认是对应项目后复用；错误进程占用时明确报错，不杀用户进程、不偷偷换端口。
- 统一日志展示准备中/就绪/失败和访问地址；界面显示项目环境状态、重新检查和新窗口兜底。启动检测不计为测试执行，不影响手动测试规则。
- 仅停止由启动脚本创建的子进程，清理Windows子进程树；已存在并被复用的校园进程不被停止。独立测试命令仍仅启动隔离的工作台测试实例，UI联动通过测试夹具验证。
- 面向演示的界面使用自然业务文案；文档和原始导出明确标注本地材料/模拟执行，不宣称真实网络验收或岗位通信。

## Verification
- 端到端：接收新交付消息 → 出现新任务 → 打开项目UI → 保存检查 → 查看API材料/生成用例/执行 → 查看工程师指派/专项用例/执行 → 查看报告/回传状态。
- 验证去重、未接收/未生成/未执行的真实状态区分、项目切换与测试互斥、取消、刷新持久化、旧配置兼容。
- 不生成未经执行的通过结论，不把模拟API响应当成目标项目真实返回；UI实际预览与本地模拟验证分别标注证据来源。
- 手动性：初始化、进入测试栏目、接收消息、解析材料或生成用例都不能自动开始下一项；未执行项保持待测试，不出现成功响应/测试报告/通过曲线。
- 演示可靠性：预览五端均能打开，手机/桌面切换、iframe不可用时的新窗口兜底、重置不影响校园业务；在1280/1440/1920宽度截图检查标题、流程和结果可读，无横向裁切。
- 引擎回归：响应方法/材料/断言匹配，场景参数编辑后需重新执行，人工补充检查单独待确认，停止保留完成记录；未完成或有问题时报告不能显示全量通过。
- 启动验证：Windows下从`qinglan-scenic`运行`pnpm dev:testing`联动七个入口；重复启动不会开第二套校园进程；端口身份错误明确失败，结束时不杀复用进程。
- 复用并调整 `tests/unit/testing-*.test.ts` 与 `tests/testing/*.spec.ts`；新流程保持API/压测零业务请求断言，UI预览和环境健康检查单独计数。
- 计划实现后执行 `pnpm typecheck:testing`、`pnpm build:testing`、`pnpm test:testing`，检查桌面和窄屏布局及项目入口不可用时的提示。
